## 覆った前提【2026-08-17。ここを知らないと過去のメモを誤読する】

### 1. 画面はRazor Pagesではない。Next.jsに全面移行した
- `src/IdPlatform.Web`(ASP.NET Razor Pages)は**プロジェクトごと削除済み**。ソリューションにも無い。
- 画面は `apps/id-platform-console`(Next.js + React + TypeScript)。同じリポジトリにnpm workspaceとして同居する。
- **C#のホストは `src/IdPlatform.Api` 1本**(業務API + OpenAPI/Scalar + コンソール向けの非公開セッションAPI)。
- 画面の認証入口・BFF・セッションはNext.js側。API側にはBFF専用の非公開エンドポイント群が増えた形。
- 根拠はADR-0013。**ADR-0013本文の「Razor Pagesは即時削除せず段階移行」は実態と食い違っていたが、ADR-0015で置き換え済み**【2026-08-17】。ADR-0013を読むときはADR-0015も併せて読む。
- **⑧-1で決めた画面の作法(セッション期限の集約・文言のresx分離・部品CSSの追記方式など)のうち、技術に紐づくものは無効になっている。**考え方(1箇所に集約する・画面に直書きしない)は生きている。

### 2. 「NBSSの協力業者関係 = guest所属」は撤回された
- **2026-08-05に承認した決定を、ADR-0007が上書きした**(2026-08-12)。2026-08-17に小林さんが新しい決定として採用。
- 新しい整理: **Membershipは「その会社が自社メンバーとして共通管理する人」にだけ作る。**職人・協力業者・顧客など一つの接続サービスの中だけで意味を持つ関係は、**接続サービスが自分で持つ**。招待元会社のMembership・guest・配属を作らない。
- **なぜ**: Membershipを作ると、会社管理コンソール・基盤ロール・組織・他の接続サービスという関係のない文脈まで関係が広がる。さらにサービス内で協力関係を止めただけで共通Userや他サービスまで巻き込んで止まる。個人情報の見え方に直結するので基盤に持ち込まない。
- **guestは廃止していない。**会社が意図的に基盤レベルの共通コンテキストを与えたいときだけ使う。
- **代わりの経路がSponsored Enrollment**(ADR-0008)。接続サービスが基盤に「外部Userの登録だけ」を依頼する。MembershipもOrganizationも作らない。**④B5の代理登録(UserとMembershipを同時に作る)とは用途が違い、併存する。**
- 画面でも「自社メンバー」と「接続サービス内の外部関係」を同じ一覧・同じ招待操作として見せない。

### 3. ログイン名はメールアドレスそのもの【2026-08-19・ADR-0017】
- レルム設定を **`registrationEmailAsUsername: true`** に変えた。ログイン名は認証サービスがメールアドレスから作る。
- **基盤アプリは管理APIにログイン名を送らない。**メールアドレスだけを送り、ログイン名は追従させる。
- **レルム設定の変更なので、環境ごとに keycloak-config-cli の適用が要る。**アプリだけ更新するとメールアドレス変更が失敗する。

## アカウントの自己管理の決めごと【2026-08-19・ADR-0017】

- **メールアドレスの変更は、新しいアドレスへ確認メールを送り、リンクで確定する。**古いアドレスは確定するまで有効。トークンはハッシュで保存し、保留中は1人1件だけ。
- **順序が要**: **先に認証サービスのメールアドレスを変え、成功してから基盤の状態を変える**。トークンも**認証サービスの呼び出しが成功するまで使い切らない**(失敗したら同じリンクでやり直せる)。
- **ログイン名は送らない**(上の「覆った前提3」)。
- **パスワードの変更は基盤で作らない。**認証サービスのアカウント画面へ、戻り先つきで送る。**基盤がパスワードを受け取る経路は初期設定のときだけ**で、そこでも保存しない。
- **退会は本人だけができる。**ただし**所属している会社があるとき**と**オーナーを務めている会社があるとき**はブロックし、先にメンバーを外す・オーナーを移すよう案内する。退会すると認証サービス側も無効化してログインできなくなる。
- **メンバー検索は氏名とメールアドレスの部分一致。メールアドレスでの検索は owner/admin にだけ許す**(一覧でメールを見せる範囲と揃える)。検索文字列の `%` と `_` はエスケープする。
- **オーナーが退職するときの案内**は、メンバー詳細に置いた文言だけ。オーナーの付け替え自体は既存のオーナー移譲を使う。

## 会社が連携を止める操作の決めごと【2026-08-19・ADR-0018】

- **撤回は「承認の印を外して一時停止に落とす」。解約(terminated)にはしない。**解約は最終状態で戻せないため、誤操作の取り返しがつかない。
- **止められるのは owner だけ**(承認は owner/admin)。止める操作は会社全体の業務に影響するため、承認より狭くした。
- **接続サービスへは専用の種別で伝える**(`organizations.contract_approval_revoked.v1`)。サービス都合の一時停止と読み分けを誤ると、会社が止めたのに再開を試み続ける実装になりやすい。変更フィード上の扱いは一時停止と同じ(世代の窓を閉じる)。
- **再開は会社の再承認から。**撤回後にサービスが単独で有効化しようとすると、既存の「承認が必要」というエラーで拒否される。
- **撤回は冪等**(二度押し・再送で状態を変えずに成功を返す)。
- **すでに発行済みの会社コンテキストトークンは失効しない**(最大15分)。画面にその旨を明記する。即時失効は⑦。
- **退会の判定では、削除予約中の会社の所属も数える。削除が確定した会社は数えない**(数えると本人が永久に退会できなくなる)。

## 会社の削除の決めごと【2026-08-19・ADR-0019】

- 状態は Active / Deleting(予約中・猶予期間内・取り消せる) / Deleted(確定)。**確定しても会社・組織の行は残す**(保持期間=C-18が未確定のため物理削除しない)。
- **確定時に片付けるのは 所属・配属・契約・招待。**所属は解除済みにし、配属は削除、契約は解約済み、未使用の招待は無効にする。**owner の所属も解除するが、通常の除名の制約(owner は除名不可)は緩めず、会社削除専用の入口を分ける。**
- **後片付けは会社1件ごとに1トランザクション。**1社の失敗が他社を巻き込まない。
- **接続サービスへは専用のお知らせ `organizations.organization_deleted.v1` で伝える。**このお知らせは**配信の窓の外でも届ける**(削除と同時に契約を解約するため、窓の中だけで判定すると誰にも届かない)。所属の解除や配属の削除は配信されないので、接続サービスは会社ごと複製を外す前提。
- **削除された会社は参照から隠す**: 接続サービス向けの契約照会 / 招待の一覧 / 招待のプレビュー / 引き取りのプレビュー。**受諾の判定(有効な会社のみ)と、見せる側を揃えるのが目的。**
- **引き取り(クレーム)の受諾APIは会社の状態を見ない。**会社が消えたせいで本人が自分のアカウントを引き取れなくなるほうが害が大きい(⑯の退会と同じ考え方)。
- **削除予約中はオーナーだけが会社設定を開けて、取消だけできる。**そのための限定的な読み取り経路(会社名・状態・削除予定日時だけ)を用意した。**会社コンテキストトークンの発行条件や既存APIの門番は緩めない。**猶予期限を過ぎた会社は出さない(取消が必ず失敗するため)。

## 外部サービス連携の決めごと【2026-08-12〜18・ADR-0007〜0012, 0014】

### Contract(会社 × サービスの契約)= ADR-0010
- 状態は `suspended` / `active` / `terminated` の3つ。加えて**会社が承認した事実**(`OrganizationApproved`)と**有効化の世代**(`ActivationGeneration`)を別々に持つ。
- **有効化には二者の同意が要る**: ①会社のowner/adminによる連携承認 ②接続サービス自身によるactive化。会社が承認しただけでは `suspended` のままで、**snapshot・変更フィード・会社コンテキストトークンはまだ使えない**。
- 片方だけで開通できると、「サービスの資格情報を持つ主体が会社の同意なしに参照範囲を開通できる」か「契約・初期設定前の会社に利用を許す」のどちらかが起きる。
- **activeなContractだけが、会社選択・会社コンテキストトークン発行・directory・変更フィードの利用条件**。
- 接続サービスは自分のContractしか操作できない(リクエストで別サービスを指定させない)。
- **会社が承認を撤回する操作のAPI契約は未確定。**

#### ⑨で足したもの【2026-08-18】
- **読み取りAPIを2本新設した。**それまで**状態を照会する手段が1本も無く**、画面が会社選択用API(`GET /v1/me/memberships?service=X`)を流用して2値に潰していた。
  - 会社向け: その会社の契約一覧。**契約が無いサービスも「契約なし」として返す**(画面がサービス一覧を出すため)
  - サービス向け: 自分の契約の照会。呼び出し元サービスはトークンから確定する
- **契約操作を監査に残す**(承認 / サービス側の有効化 / 一時停止 / 終了を別記録)。それまで契約の監査が1件も無かった。ADR-0010の要求。
- **画面は6状態**: 未申請 / 開通待ち / 利用中 / 一時停止中 / 解約済み / **状態を取得できません**。最後の1つはAPI通信失敗用。**それまで通信失敗が「未利用」と表示されていた**(障害と未契約が区別できなかった)。
- **サービス一覧の正本が二重になっている**: 並びは環境変数、状態は新API。**要整理**。

#### 【重要な構造上の制約】利用開始の操作は会社コンテキストの外側にある
**基盤は「契約が有効な会社」にしか会社コンテキストトークンを発行しない**(`sts.contract_not_active`)。開通前の会社には出ない。つまり**接続サービスの「開通する」操作を、会社コンテキストトークンでは原理的に保護できない。**

- Growthが採った方式: **BFFが基盤のユーザーアクセストークンを自分のAPIへ渡し、基盤の `GET /v1/me/memberships` で本人と会社ロールを再確認する**(ADR-0014が「接続サービスは認証後にユーザー認証トークンで `/v1/me` と `/token/context` を使う」と定めている)
- **NBSSでも必ず同じ壁に当たる。**接続サービスを増やすときに毎回思い出すこと。

#### `/activation`(owner単独で承認と有効化を両方やる経路)
- ADR-0010に書かれていない例外として存在する。エンドポイントのコメントには「接続サービス側にユーザー管理画面を持たせず、会社単位の利用開始を基盤へ集約するため」とある。
- **⑨では動作を変えず、OpenAPIに非推奨の注記だけ入れた。**Growth側に開通処理ができるまでの経過措置として残している。
- **廃止は未実施。**廃止するときは新しいADRで記録する。

### 同期はsnapshot + 変更フィード = ADR-0011
- **プッシュ配信(SNS→SQS)より先に、こちらを作った。**プッシュだけでは取りこぼしを復旧できず、結局突合の仕組みが要るため。
- 接続サービスはローカルの参照用複製(read model)を持つ。呼び出し元サービスは**トークンから確定**する。
- **見える範囲は「呼び出し元サービスのactiveなContract」と「Membershipのサービス範囲」で決まる。**見えないIDは存在しないIDと区別できない応答にする。
- 応答とイベントに**PIIを載せない**。表示名はID参照APIで解決する。
- **初回開通・Contract再開・会社の再有効化・カーソル復旧のときはfull snapshotを取り直す。**その後は差分を取る。
- at-least-once。`eventId` で冪等化。**空ページでも次のカーソルを必ず保存する。**
- カーソルは不透明で呼び出し元サービスに束縛。**Contractのactivationごとにストリームの世代を区切り、停止期間中の変更を再開後に遡って配信しない。**
- snapshotの置き換え・処理済みイベント・カーソル保存は接続サービス側の**同じローカルトランザクション**で確定する。

### NBSSの扱い = ADR-0009
- **NBSSは一つのServiceClient**(service code = `nbss`)。出面・在庫・設備などの機能別に分けない。
- Contractは「その会社がNBSS全体に入れるか」だけを表す。**activeにしても出面や在庫が自動で有効になるわけではない。**機能別の契約・メニューはNBSSが管理する。
- **基盤ロール(owner/admin/member/guest, unit admin)を接続サービスの業務権限に変換しない。**承認者・職長・現場管理者などはNBSSが持つ。
- Membershipを持たない職人には**招待元会社の会社コンテキストを発行しない**。

### Sponsored Enrollment = ADR-0008
- 接続サービスが先に自分の中で関係を保留状態で持ち、推測しにくい相関IDを発行する。
- 基盤へ渡すのは**氏名・連絡先・相関IDだけ**。会社ID・Membership・業務権限は渡さない。
- 基盤は同じ本人がいれば再利用、なければMembershipなしの未クレームUserを作る。**依頼側に「既存Userがいたか」が分かる応答は返さない**(在籍の探り出し防止)。
- 基盤が期限付き・1回だけ使える・取り消せる本人設定URLを送る。**接続サービスにパスワードを入力・保存させない。**
- 完了後は**事前登録された戻り先だけ**を使って接続サービスへ戻す。
- **招待の取消・期限切れ・協力関係の停止は接続サービス側の関係を止めるだけ。**既存User・他社との関係・他サービスの利用を止めない。

### API契約の公開ルール = ADR-0012
- 機械可読な正は**C#実装から生成するOpenAPI**。閲覧UIのScalarは**交換可能なrenderer扱い**で、アーキテクチャの依存先にしない。
- エラー形式は RFC 7807 互換の `application/problem+json` に統一。
- **外部向けの文書に認証製品名(Keycloak等)を出さない。**「ユーザー認証トークン」「Organization context token」「サービスアクセストークン」という公開概念を使う。※**社内の設計書でKeycloakと書くのは制限していない。**日本語で書くときは `Organization context token` =「**会社コンテキストトークン**」(→[[terminology]])。
- 開発環境限定で公開し、本番相当では404。

### 接続サービスの独自ログイン画面 = ADR-0014
- 接続サービスがサービスの文脈に合った入口画面を持ってよい。ただし**パスワードをAPIで受け取らない**。
- 基盤が `GET /v1/auth/config` と `POST /v1/auth/requests` を提供し、Authorization Code + PKCE(S256)で基盤の認証画面へ遷移させる。事前登録済みの clientId と redirectUri だけを受け付ける。
- 「メールとパスワードを基盤APIへ送ってトークンを返す」形のAPIは提供しない。

## フロントエンドの決めごと【ADR-0013 + ADR-0015】
- **ブラウザにアクセストークンを持たせない。**画面のサーバー側がトークンを預かり、ブラウザにはセッションIDだけ渡す。
- **デザイン値は `shared/design-tokens` のJSONが正**で、そこから生成したCSS変数を使う。**画面のCSSに色・余白・高さ・角丸・影を直接書き足さない。**Keycloakのログイン画面テーマも同じトークンから生成する。
- 共通UIは `shared/ui/primitives` と `shared/ui/patterns` に分ける。業務画面は `features/{domain}`。`app/` はルーティングとレイアウト中心に薄く保つ。
- 現在のv1デザインと、リリース前大改修用の `release-placeholder` テーマを分離。**最終デザインが固まるまで `release-placeholder` を正式テーマにしない。**
- Storybook / Vitest / Next build / トークンのずれ検査 / lint / typecheck をCIに追加済み。カタログの実体はHTMLではなく**Storybook**。
- **認証セッションの入口を1か所に保つ**(ADR-0015)。ログイン開始・コールバック・ログアウトの終端を複数のホストに分散させない。

## 過去のフェーズで確定した決めごと(そのまま有効)

### ⑤権限マトリクスの全面強制
- OrgPermissionMatrix(表と1:1・**認可の正**)/ OrgUnitPath / UnitAdminAuthority
- 監査は**業務コミット→監査記録の順・監査失敗は業務応答を壊さない**。afterはPIIなし
- 招待: unit admin=自サブツリー配属前提(組織必須)・自分が出した招待だけ取消/一覧。他人の招待=NotFound
- 組織: 同一親下の名前一意・深さ5・上限1000・削除ガード409。**親の付け替えとpath書き換えは必ず対**(片方だけだと権限事故)
- 配属: 追加・解除=owner/admin全域・unit adminは自サブツリー / **フラグ付与・剥奪はowner/adminのみ**
- メンバー管理: **adminが絡むロール変更はowner専権** / owner除名・owner化不可 / 自分自身の除名不可 / **除名時は配属も一括解除**
- 実装方針: 会社×ロール=API層(RequireOrgRole)、サブツリー・所有者条件=Application層の共通ポリシー1箇所

### ④B5 未クレームUser(代理登録と引き取り)
- **B5-1 代理登録**: owner/adminのみ。**順序は事前確認→ユーザー作成→所属作成**(でないと権限不足でメールが焼ける)。自社の未クレームUserは再利用。二重登録と除名済みの残存は409。**IdPアカウントを作らない**
- **B5-2a クレーム本体**: 期限14日 / 代理登録時に案内メール自動送信 / 再送API(owner/admin)/ preview・accept(いずれも認証不要)
  - **`User.Claim()` は引数なし**。引き取り時点でKeycloakアカウントは無く、`idp_sub` はIdP同期が後から埋める
  - **やり直しの代理登録で案内メールを二重に送らない**のは条件式でなく**構造**で担保(早期returnでメール投入に到達しない)
  - **使用済みトークンの救済はクレームには入れない**。所有権が移る操作で二度目の成功を返す意味がない
- **B5-2b 招待経由の引き取り**: 招待の宛先が未クレームUserなら受諾が引き取りとして成立。根拠は「招待メールを受け取れた=そのメールの持ち主」(B4-2の整理の延長)
  - **なぜ必要か**: 下請けは元請け複数が常態。X社が代理登録した人にY社が招待を出しても、未クレームはログインできず受諾できないという詰まりが日常的に起きる

### ⑥ はじめての会社が作れる状態にする
- **⑥-1**: `users.mail_deliveries` を新設(ユーザー棟から会社棟のキューへ書かない)。検証トークンは**24時間**。**失敗の理由を区別しない** / **再送は形式が正しければ常に202**
  - **使用済みトークンの救済**: 企業のメールセキュリティ製品が**リンクを先読み**して本人のクリック前にトークンを消費するため
- **⑥-2**: 会社作成は**マトリクス対象外**。門番は**メール検証済み**と**ownerを務める会社数の上限10**。**門番の判定はユースケース側**(API層だけだと入口が増えたとき素通り)
- **⑥-3 組織ツリー**: フラット配列+parentId+depth+**memberCount(直属のみ)**。ページングなし。**unit adminにも全体を返す**(祖先のパス表示に要る)。**path順=作成順**
- **⑥-4 メンバー一覧**: **メールは owner/admin にだけ**。氏名はContracts経由で**1回だけ**まとめて引く
  - **【重要な学び】カーソルに作成時刻を使ったら、まとめて作られた行がページ境界でエラー無しに消えた**(結合テストが検出)。`orgs.memberships` に**連番(identity)列 seq** を足して解決。**新規の一覧は連番を既定にする**

### ⑧-1・⑧-2a・⑧-2b で確定し、いまも有効な考え方
- **画面のエラー分岐はHTTPステータスではなく problem+json の `code`**。APIに繋がらない・タイムアウトは**例外のまま**にして握りつぶさない
- **個人情報をクエリ文字列に載せない**(履歴・Referer・アクセスログに残り後から消せない)
- **A11(状態の説明画面)は HTTP 200 のまま**。4xxにすると監視のエラー率に日常的な出来事が積み上がる。**未知の理由コードは列挙に丸め、受け取った文字列を画面に出さない**
- **`users.invalid_registration` は項目を決め打ちせずフォーム全体の案内にする**(APIが「氏名が空」と「メール形式不正」を区別しないため)
- **セッションの期限判定は自前の1か所に集約**する。「共有端末だけ1時間」と「切れた理由の区別」を扱う必要があるため
- **Cookie自体の期限は通しの上限に合わせ、無操作は最終操作時刻の印で判定**。Cookie側を短くすると**時間切れを検知する前にCookieが消えて理由を出せない**
- **アプリ側にHTTPSリダイレクトは入れない**(HTTPSはCaddyが終端)。これが無いと**OIDCの `redirect_uri` が `http://` になりログインが通らない / 監査ログの接続元IPが全部Caddyになる**。**どちらもlocalhostでは再現せず、CIも単体テストも検知できない**。信頼するプロキシは絞る
- **⑧-2b-1のイベント設計**: イベントを積むのは「未検証→検証済みへ変わったとき」だけ。無条件に積むと**案内メールが繰り返し送られる**
- **送信の前に必ずIdPアカウントの用意(冪等)を通す。**outboxの取り出し順の都合で、先行するイベントがバックオフ中だと後から積まれたものが先に処理され、`idp_sub` が空のまま送ろうとする
- **パスワード設定メールに `redirect_uri` を渡さない**(認可セッションにstate/nonce/PKCEが無く必ず失敗する)
- **メール送信の案内で「送りました」と断定しない。**outbox経由の非同期送信で、画面が出る時点ではまだ送っていない。断定するとSMTP障害時に無音の失敗になる

### ⑨ 契約状態の可視化で確定した考え方【2026-08-18】
- **「状態を取得できません」を独立した表示として持つ。**通信失敗を「未契約」「未利用」に混ぜない。混ぜると障害中に運用が誤判断する
- **一覧APIは「まだ存在しないもの」も表現できる形にする。**契約が1件も無い会社でもサービス一覧が返らないと、画面がサービスを並べられない
- **状態を持つ層と、状態を見せる層の間に読み取りAPIを置く。**書き込みAPIの戻り値だけでは画面は作れない(⑨以前は読み取りAPIが1本も無かった)

- **画面の文言はコードに直書きしない。**(Razor時代はresxが正だった。Next.js移行後の文言の置き場は `features/management/labels.ts` 等)
- **モジュールをまたぐ検索は、相手モジュールのContracts経由でIDだけを受け取って絞り込む**(⑮のメンバー検索。JOINは禁止・N+1も禁止)
