# 技術スタック(2026-08-04 確定 / 2026-08-13 フロントエンド追加 / 2026-08-18 pnpmに統一)

## バックエンド・インフラ
- 実装言語: **C#**(.NET 10)
- サーバー: AWS **EC2(Ubuntu)**(v1は単一EC2許容。可用性要件はテスト期免除・リリースゲート=概念設計書§3.6)
- DB: AWS **RDS(PostgreSQL)**【確定】。**ID基盤とGrowthは同じインスタンスを共有し、Growthは `growth` スキーマに分離**
- **IdP: Keycloak 自前運用**: テスト期はアプリと同一EC2の別コンテナ、RDSに専用DBで共用。レルム1つ、環境ごと独立。26.x系固定・**アップグレードはCI定常作業(採用条件)**。SMS OTPは標準非搭載→職人向けサービス時に再評価
- ファイル: **S3**
- メール: AWS **SES**想定(テストはMailpit)。**パスワード設定・再設定のメールだけはKeycloakが自分のSMTPで直接送る**ため、差出人と文面の管理先が2系統になる(差出人は基盤側に揃えてある)
- TLS証明書: **Caddy**の自動証明書(EC2直配置の暫定解。ALB移行時=§3.6トリガーでACMに切替)
- CI/CD: **デプロイまでCI/CDで完結**。**初期構築(プロビジョニング)もCI化し、サーバーにSSHせず運用**

## フロントエンド【2026-08-13 追加・ADR-0013】
- 実装言語: **TypeScript**
- **Next.js(App Router)+ React**
- **ID基盤の画面**: `apps/id-platform-console`
- **Growthの画面**: `apps/growth-web`。BFF兼用
- テスト: **Vitest**。部品カタログは **Storybook**(ID基盤側のみ)
- **デザイン値はJSONのデザイントークンが正**で、そこから生成したCSS変数を使う。**画面のCSSに色・余白・高さ・角丸・影を直接書き足さない**
- **ブラウザにアクセストークンを持たせない**(BFFがトークンを預かり、ブラウザにはセッションIDだけ渡す)
- **なぜ移行したか**: 画面数とUI状態が増えるにつれ、Razor Pagesへ直接HTML/CSS/JSを積む形では部品の重複・デザイン改修時の差し替え漏れ・トークンの扱いのばらつきが起きやすくなるため。**旧 `src/IdPlatform.Web` は廃止済み**

## パッケージマネージャー: pnpm 10.15.1【2026-08-18 統一】
**両リポジトリとも pnpm。**基盤は npm workspaces から移行した(それまで基盤=npm・Growth=pnpm で混在していた)。

- 各リポジトリのルートに `packageManager: "pnpm@10.15.1"` を明示、`pnpm-workspace.yaml` でワークスペースを定義
- **`packageManager` を書かないと corepack が勝手に書き足す。**基盤で実際に起き、`package.json` が常に汚れてブランチ切り替えが失敗する状態になっていた。**新しいリポジトリでは最初から明示する**
- **Storybook は pnpm の厳密な node_modules でも動いた**(移行時にいちばん警戒した箇所。巻き上げの回避設定は不要だった)
- Node は 22 系

## API文書【2026-08-10 追加・ADR-0012】
- 機械可読な正は **C#実装から生成するOpenAPI**。閲覧UIは **Scalar**(交換可能な表示UI扱いで、アーキテクチャの依存先にしない)
- **開発環境限定で公開し、本番相当では404**
- エラー形式は RFC 7807 互換の `application/problem+json` に統一

## PostgreSQL選定理由【顧客に聞かれたら即答する用・小林さん依頼】
1. **データ整合性・移行の安全性**: トランザクショナルDDL — スキーマ変更が失敗しても中途半端にならず確実に戻る
2. **マルチテナントセキュリティ**: Row-Level SecurityをDB層の防御線にできる(多層防御)
3. **柔軟なデータ表現**: JSONB+部分/式インデックス
4. **実績と将来性**: SaaS・金融系で採用実績厚。RDSフルマネージド、コストはMySQL同等
5. **ライセンスの自由度**: 寛容なPostgreSQLライセンス
(補足: MySQLと致命差はなく、ゼロベース構築のため機能優位を採用、が正直な経緯)

## Keycloak選定理由【顧客向け即答用】
1. **必須基準を標準機能で充足**: Standard Token Exchange(26.2で正式サポート)・OIDC Back-Channel Logout
2. **コストがユーザー数に比例しない**: ToC(施主・職人)拡大でも費用一定。Auth0はMAU課金で不整合、Cognitoは必須機能未達で除外
3. **データが自社AWS内**: 個人情報保護法の説明が単純
4. **ログイン画面の完全カスタム**が可能
(留意: 運用責任は自社。パッチ追随をCI定常化するのが採用条件)
**注意**: **外部に公開するAPI文書には認証製品名を出さない**という別ルールがある(ADR-0012)。顧客・社内向けの説明でKeycloakと言うことは制限していない。
