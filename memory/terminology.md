# 用語統一(2026-08-04 確定 / 2026-08-17 改訂)

## 基本の対応表(これが正)

| 概念 | モデル上の名前 | 日本語 | 例 |
|---|---|---|---|
| 契約・課金・招待・会社選択の単位 | **Organization** | **会社** | A株式会社、元請けA社、協力会社B社、工務店C |
| 会社の中のツリー構造 | **OrgUnit** | **組織** | 開発部、建設部、設計部、開発部→商品開発課 |
| ユーザー×会社の関係 | **Membership** | **所属** | 田中さんはA株式会社のmember |
| 所属×組織の関係 | **Assignment** | **配属** | 田中さんは開発部と商品開発課に配属 |
| 配属に付与する管理フラグ | **unit admin** | **組織管理者** | 開発部の組織管理者は商品開発課も管理できる |

- 派生語も揃える: **親組織 / 子組織 / 所属組織 / 組織ツリー / 組織階層 / 配属先組織**。
- **`unit admin` という英語表記はそのまま使う**(識別子として定着している)。日本語で説明するときは「組織管理者」。
- 用語集は概念設計書のセクション0が正。

## 2026-08-17 の改訂点

**OrgUnitの日本語表記を「部署」から「組織」へ統一した(小林さん承認)。Organizationは「会社」のまま変えていない。**

- 画面(Next.js)はすでに「組織」「親組織」「子組織」「所属組織」「組織管理者」「組織ツリー」で統一されていた。C#のAPI層も「組織」へ統一済み。残っていた設計文書とメモリを揃えた。
- **これまであった「『組織』という語を単独で使わない」というルールは撤回された。**いまは「組織=OrgUnit、会社=Organization」で意味が確定しているため、単独で使ってよい。

## トークンの呼び方【注意】

- **`Organization context token` の日本語は「会社コンテキストトークン」**。どの会社の文脈で操作しているかを表すトークンであり、OrgUnit(組織)とは無関係。「組織コンテキストトークン」と書かない。
- **英語の識別子 `organizationContextToken` は変えない。**ADR-0012で定めた公開概念名であり、OpenAPI上のセキュリティ方式名にもなっているため。
- 公開概念のトークン名は3つ(ADR-0012。外部向け文書ではこの3つを使い、認証製品名を出さない):
  - **ユーザー認証トークン** — 本人が誰かを表す
  - **会社コンテキストトークン**(`Organization context token` / `organizationContextToken`)— どの会社の文脈で操作しているかを表す
  - **サービスアクセストークン** — 接続サービス自身が基盤を呼ぶときのもの

## ADRは旧表記のまま残る【読み替えが必要】

**リポジトリの `docs/adr/` と、プロジェクト側の控え `repo-docs/adr/` のADRは、旧表記「部署」のまま残っている。**ADRは「書き換えて履歴を消さない」運用のため、今回の用語変更では触っていない。

- 読むときは **「部署」= 組織(OrgUnit)** と読み替える。
- 同じ理由で、日付付きスナップショット文書(`id-platform-review-20260804.md` / `id-platform-usecases-v0.1.md`)も本文は当時の表記のまま。

## 英語の識別子は変えない

日本語の呼び方を変えただけで、モデル・API・DBの名前は一切変えていない。

- 型・概念名: `OrgUnit` / `Organization` / `Membership` / `Assignment` / `unit admin`
- APIパス: `/v1/orgs/{orgId}/units` など
- DB: `orgs.org_units` / `orgs.unit_assignments` / `is_unit_admin` など
- トークン: `organizationContextToken`

## 2026-08-12以降に増えた用語

- **契約** = Contract = 「会社 × 接続サービス」1件。その会社がそのサービスを使えるかどうかだけを表す。状態は `suspended` / `active` / `terminated`。**会社側の承認とサービス側の有効化の両方が揃って有効になる**
- **サービス固有の外部関係** = 職人・協力業者・顧客など、**一つの接続サービスの中だけで意味を持つ関係**。基盤のMembershipは作らず、接続サービスが自分で保持する。**「guest所属」とは呼ばない**(2026-08-05の言い方は撤回された)
- **Sponsored Enrollment** = 接続サービスが起点になって、基盤に外部Userの登録だけを依頼する仕組み。MembershipもOrganizationも作らない。日本語の定訳は決めていない
- **directory API** = 接続サービス向けの参照API(User/Organization/Membership/OrgUnitのsnapshot)。**呼び出し元サービスのactiveなContractの範囲でしか返さない**
- **変更フィード** = 差分を取りに行くAPI。snapshotとセットで使う
