## ID基盤との連携の作り【ここが一番重要】

### 認証: BFFパターン
- Growth Web は **OIDC(client id `growth-web`)でID基盤にログイン**する。
- **アクセストークン・リフレッシュトークン・IDトークンをブラウザに渡さない。**BFF側のセッションストアに保存し、ブラウザにはHttpOnly Cookieで**ランダムなセッションIDだけ**を渡す。
- **Growthはパスワードを一切扱わない。**
- **サインアップ画面をGrowthに作らない。**アカウント作成は基盤の責務(概念設計 §3.5)。GrowthのLPからは基盤のサインアップへリンクする。

### 会社コンテキスト: context token
- Growth API へのリクエストには、**ID基盤が発行した context token**(`aud=growth`)を使う。
- Growth API 側は ID基盤の `/.well-known/jwks.json` を使って**JWKS検証**する(基盤に問い合わせない)。
- **context token が401で拒否されたら、BFFが一度だけ再発行して同じリクエストを再送する。**

### サービス間連携: directory API
- Growth API は ID基盤の**サービス向けMembership snapshot API** `GET v1/service/orgs/{orgId}/memberships?limit=&cursor=` を呼び、指定会社のactiveな所属を検証する。
- この呼び出しの認証は **OAuth2 client credentials** でサービスアクセストークンを取得する方式。**本番では静的なトークンを使わない**。
- 401/403のときはキャッシュしたトークンを捨てて1回だけ再取得・再試行する。

### 契約の開通(二者同意の2段目)
ID基盤の Contract は**会社の承認**と**サービス側の有効化**の両方が揃って有効になる(ADR-0010)。**Growthはこれまで2段目をやっておらず**、基盤側の経過措置(ownerがボタン1回で承認と有効化を両方やる `/activation`)に頼っていた。それを本来の形にした。

- Growth API に2本: **契約状態の一覧**と**開通**。開通は「基盤で自契約を照会 → 開通待ちを確認 → Growth側の初期化 → 基盤の契約を有効化」の順で固定
- **Growth側の初期化は現時点で中身が無い。**将来ここに入る場所だけ作ってある
- **冪等**: すでに有効なら基盤の更新APIを呼ばずに成功を返す
- 実行できるのは対象会社の **owner のみ**。判定はID基盤の会社ロールに委ね、**Growthの業務権限とは混ぜない**
- ポータルは6状態(利用中 / 開通待ち / 未申請 / 一時停止中 / 解約済み / 状態を取得できません)。**通信失敗を「未利用」と混ぜない**

#### 【重要な構造上の発見】開通APIを context token で守れない
**ID基盤は「契約が有効な会社」にしか context token を発行しない**(`sts.contract_not_active`)。開通前の会社には出ない。つまり**開通の操作だけは、Growthの通常のAPI認証方式(context token)では原理的に保護できない。**

- 採った方式: **BFFがID基盤のユーザーアクセストークンをGrowth APIへ渡し、Growth APIが基盤の `GET /v1/me/memberships` で本人と会社ロールを再確認する**
- **このとき `service` パラメータを付けてはいけない。**付けると契約が有効な会社しか返らず、開通前の会社を検証できない
- 根拠: ADR-0014 が「接続サービスは認証後にユーザー認証トークンで `GET /v1/me` と `POST /v1/token/context` を使う」と定めている
- **副作用: Growth API がユーザーアクセストークンを扱う経路が新設された。**信頼境界が広がるので、他の用途へ安易に流用しない
- **同じ問題は他の接続サービス(NBSS)でも必ず起きる。**「利用開始の操作は会社コンテキストの外側にある」と覚えておく

### ログアウトの作り【2026-08-18】
**基盤コンソールとは方式が違う。**基盤はGETリダイレクト、**Growthは中継ページを1枚挟んでフォームでPOST**する。`id_token` をURL・ブラウザ履歴・アクセスログに残さないため。

- 中継ページは**待機表示(「ログアウトしています」+自前SVG)**を出す。ダークモードと「動きを減らす」設定に対応
- **中継ページはアプリのCSSもデザイントークンも読み込まない**(Route Handlerが直接HTMLを返すため)。色はトークンの値を**書き写している**。**承認された例外**だが、**テーマ変更時に取り残される。CIでも検知できない**
- ログアウト後の戻り先は **`/auth/signin`**(LPの「ログイン」と同じ入口)。そのホップだけ**再認証を強制**する
- **再認証の印はURLではなく短命Cookieで渡す。**Keycloakの戻り先は**完全一致で登録**されるため、クエリを足すと拒否される
- **CSPに注意。**`script-src` は nonce 方式なので、中継ページのインラインscriptには**nonceが要る**。`form-action` には**Keycloakのオリジンを許可**する必要がある。**どちらかを外すと白い画面で止まる**(実際に起きた)

### 責務境界
- **ユーザー認証・会社・所属・招待・共通プロフィールの正はID基盤。**GrowthはUserId/OrgId/MembershipIdを**参照するだけ**で、ID基盤側の所属データを作成・更新しない。
  - **例外は自分の契約の有効化だけ**(基盤が認めた経路)
- **Growthの業務権限(Growth adminなど)はGrowthが持つ。**ID基盤の管理ロールを業務権限として流用しない(ADR-0007/0009と同じ考え方)。
  - ただし**初回だけはID基盤のownerがbootstrapできる**。以降はGrowth admin限定。
- Growthが担当するのは見積・案件・顧客・AI解析・Growth内の業務権限。

### DBの置き方
- **ID基盤と同じPostgreSQLインスタンスを共有しつつ、`growth` スキーマに分離する。**

## CI
- `pull_request` と `main` への push で起動。**PostgreSQL 17 のサービスコンテナを立てて実DBに対して検証する**(ID基盤のCIが結合テストを回さないのと対照的)。
- 検証は `pnpm run ci` 一本: コメント規約チェック → デザイントークンチェック → フロントlint → フロントtypecheck → フロントtest → フロントbuild → バックエンドbuild → バックエンドtest。**どれか1つ落ちると全体が落ちる**
- **ブラウザE2Eはワークフローに無い**(未着手)。
- **CIの結果をPRコメントに書く仕組みが無い**(ID基盤にはある)。**`get_check_runs` と `get_status` は権限不足で403**になるため、クラウドセッションから状態を知るには `search_pull_requests` に `status:` を投げて判定する。**確定まで40分以上かかることがある**
